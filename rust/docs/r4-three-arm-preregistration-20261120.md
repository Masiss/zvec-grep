## 1. Question and arms

Primary product question: does zvec-grep enable an external AI agent to
produce more correct, better-grounded answers with less unnecessary
source/context consumption and acceptable operational complexity?

- **Arm A — ordinary hybrid search control.** The agent uses the existing
  ordinary search capability (`search` with hybrid/fts/vector/rg modes,
  bounded results, per-file hashes for fresh items) plus `status`.
  Nothing is artificially weakened relative to the product surface.
- **Arm B — engine-managed R4 (control identity: corrected baseline32).**
  The engine-managed deterministic workflow under the frozen baseline32
  budget (≤6 calls/≤3 rounds/≤32 reads/≤24 KiB pack), executed through the
  adapter with the shared cumulative pool. Two preregistered sub-modes:
  - *B-plan (primary)*: `run_with_plan` with a **fresh blind plan**
    generated by the same external model from the 12 question texts plus
    folder hints only (no gold, no cases, no receipts), model calls,
    tokens and latency accounted. This is the identity of the corrected
    baseline32 (0.4861) reproduced with corrected accounting.
  - *B-frozen (diagnostic only)*: the frozen blind plan
    (`r4b-blind-plan-20261117.json`, SHA-256 `e8a33dde…`) for
    reproduction diagnostics; it must NOT be used as hidden answer
    knowledge in the fresh blind comparison and is reported separately.
  - *B-noplan (secondary diagnostic)*: question-only `run` — the weaker
    control; any comparison against Arm C using B-noplan alone is invalid.
- **Arm C — agent-driven evidence tools.** The agent freely orchestrates
  `search`, `symbol`, `facts`, `evidence`, `verify` under the same
  cumulative budget; no planner, reranker or selector assists it.

## 3. Fairness conditions

- Same external model identity and configuration across arms; requested
  and served model identity (provider-reported model id plus any system
  fingerprint/revision metadata) recorded per call; if the provider
  cannot supply immutable revision identity, the limitation is reported
  and the frozen identity gate applies — no invented versions.
- Fresh isolated answerer session per case×arm; answerers receive only:
  the case question, the arm's tool contract, remaining-budget state, and
  tool envelopes. They never receive gold, C3 checklists, expected
  answers, prior solutions, handoffs, corpus paths or session paths.
- Equivalent answer instructions (three conclusion classes, citation
  rules per `REPORT-CONTRACT.md`, abstention allowed), identical
  verification policy (final pack revalidation; `verify` is byte-bounded
  and always possible), identical grading.
- Rounds are controller-owned (one model turn = one round, capped at 3);
  answerer round declarations are contract violations.
- All work is accounted: external calls, engine internals (Arm B
  `internal_calls`), reads, delivered bytes, wall time, model calls,
  tokens, latency. Arm B's internal reads are reported via workflow
  stats, never hidden.
- Answers and evidence are frozen and hashed before grading; the grader
  runs in a separate context with the frozen C1–C6 rubric and C3
  checklist released only to it. If the same model identity grades,
  context separation is demonstrated and the limitation disclosed.

## 4. Metrics (frozen definitions)

- Answer quality: C1–C6 per case (12 = PASS, 8–11 PARTIAL, ≤7 FAIL);
  C3 required-step scores; claim-level citation support; negative-claim
  correctness; source-vs-deployment discipline; abstention quality.
- Retrieval: Recall@10 under the frozen macro definition (R0 target
  0.5722 unchanged), selected/delivered evidence spans, distinct files,
  calls, rounds, read files/ops, exact delivered bytes.
- Resources: local-tool wall (p50/p95 over ≥5 samples, cold and warm
  labeled), external inference latency, model calls/tokens, per-process
  RSS, adapter incremental memory.

## 5. Decision rules (fixed before outcomes)

- If Arm A matches or beats Arm C quality at lower complexity →
  recommend ordinary search as the default external-agent surface and
  identify the actual marginal value of R1/R2/R3 capabilities.
- If Arm B shows measurable advantage → identify which capabilities
  justify retaining engine-managed work; do not remove the retained
  workflow on speculation.
- If Arm C wins → identify the minimal tool surface and evidence contract
  to keep, plus deterministic responsibilities that may become redundant;
  no public promotion of the experimental adapter.
- If no arm qualifies (any frozen gate fails) → NO_GO/INCONCLUSIVE with
  failure attribution from actual traces; no automatic retrieval-tuning
  campaign.
- Development-set preference is not R4 completion, MVP qualification or
  release readiness.

## 6. Resource gate applicability (recorded, not adjusted)

Frozen local-tool gates: warm p95 ≤ 1 s for bounded local operations;
≤ 3 s local-tool wall per investigation. Measured under process-per-call:
bounded ops 0.01–0.07 s (PASS); indexed FTS 0.50 s (PASS); hybrid/vector
1.23–1.35 s (FAIL vs 1 s, model load per process); Arm B workflow
median 3.1–4.7 s warm (FAIL vs 3 s investigation gate as measured).
These gates bind the product path; for the benchmark they are reported
per arm and do NOT block the answer-quality comparison, whose frozen
budgets are call/file/byte-based. No acceptance target is changed; a
future persistent-engine correction is noted as an option only if the
architecture decision requires it.
