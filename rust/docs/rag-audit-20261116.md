## 2. Discrepancies found, and their resolution

### A1. "Pool 12/25" vs "20/25 (or 19/25) gold was never retrieved" — **CONTRADICTORY; the 20/25 claim is INVALID**
12/25 is computed by the harness from `WorkflowOutcome::candidates` (authoritative,
present in every receipt). The 20/25 figure came from the new `traced` vector. That
vector was **not exhaustive**: `select` records decisions under the *widened* unit
while the pool is keyed by the *pooled* unit, so the two cannot be joined; the
backfill in `finish()` then labels untraced pooled units `rejected_items`.
Reproduced: an exhaustive-trace run reports only `rejected_items: 6521` and
0 selected under any join — an impossible value (the same run selects 6/25).
Correct interpretation: gold absent from the pool = 25 − 12 = **13**, of which
D02 (6) and D12 (2) dominate. The `r4-preservation-20261116` report and memory
entry claiming "20/25 had no candidate" are **wrong and superseded by this audit**.

### A2. "2,085 `rejected_file_budget`, all other reasons zero" — **ARTIFACT, not evidence**
The admission file budget was checked in `accept()`, i.e. *before* any candidate
reached ranking. Only 96 files could ever be pooled, so essentially every later
unit was rejected there; score/item/cap/byte decisions are computed in `select`
and could not appear. The count therefore proves only *where the check sat*, and
it positively **masked** selection-stage losses. After the audit's rank-aware fix
(`eb143a1`) the same instrumentation still shows a single reason, now
`rejected_items`, for the same structural reason. Any future claim of the form
"mechanism X drops no evidence" must not be inferred from this trace.

### A3. "hybrid 24 KiB = 0.0000" — **unit-definition mismatch, invalid**
The `hybrid_byte_bounded` arm sizes *entity ranges* returned by the context API
(single spans of 30–56 KB), so nothing fits in 24 KiB. The deployable hybrid sends
*matched snippets*; sized that way (CLI `--preview detail`, greedy fit to 24 KiB)
the baseline is **0.1667**. The 0.0 arm is retained in the receipt for
transparency but must not be quoted as the baseline.

### A4. Macro vs span counts — **not a contradiction**
0.4167 is the macro mean; the same run covers 8/25 spans (0.3200). Both are
correct under their own definitions. Every report must state which is quoted;
`r4b_paired` prints the macro one while per-case lines print counts, which is the
source of earlier confusion.

### A5. 7/6, 9/5, 12/5, 12/6 — **different code states, same metric**
Pool/selected pairs map to commits: 7/6 → `711a4f7` (R4, no discovery routes),
9/5 → `53c3bf3` (filtered retrieval, symbols, facts), 12/5 → `48130d9` (hybrid
base + P1, before compaction), 12/6 → `cdfb014` (compaction + breadth + dedup).
They are not contradictory measurements of one system; the pool grew and the pack
converted one more span.

### A6. Earlier causal claims — historical errata
- "D04 lost to a stale/hash rejection" (`r4-discovery-results`) — **wrong**: the
  `missing` gap was the abstention diagnostic `required code token absent`. Already
  corrected in `r4-query-feasibility-and-selection-audit-20261115.md` §0.
- "All four selection losses are capacity, not verification" — **verified** on the
  pre-fix pool (2 per-file cap, 2 item/byte ranking, 0 verification).
- "Scan-order starvation by generated JSON dumps" — **verified** for the original
  `rg` stage; it is not the current bottleneck.
- "Reserved hybrid slots preserve the hybrid ranking" — **falsified** (E3 of
  `cdfb014`: 0.2361). Reservation is route-label based while ranking is region
  based.

## 7. Unified evaluation contract (proposal for all later missions)

1. **Baseline** = hybrid question route with *snippet* units, greedy fit to
   24 KiB, measured in the same harness as the arm (never a CLI/entity proxy).
2. **Report three numbers separately**: pool coverage (gold in candidate pool),
   selected coverage, macro Recall@10 — with the span counts beside each.
3. **Every candidate carries one terminal decision** from a typed set, and the
   trace must join pool↔selected by construction (a test asserts
   `pool.len() == traced.len()` and that every selected span appears as `selected`).
4. **Stage-attributed loss** is reported per gold span: `not_retrieved`,
   `admission`, `pool`, `ranking`, `packing`, `verification`, `selected`.
5. A metric that cannot be reproduced from its receipt is marked **UNVERIFIED**,
   never quoted as a result.
6. No generalization claim from D01–D12; held-out untouched.

## 8. Hypotheses that must not be retried (falsified with receipts)

- Code-token lexical discovery as the primary route (0.2778 vs hybrid 0.4167).
- Reserved intra-workflow "hybrid slots" as a way to preserve hybrid ranking (E3).
- Increasing the candidate pool by loosening admission, without new retrieval
  (pool 434→953 units, gold unchanged).
- Breadth-first subject rotation as a recall lever (no change).
- Bigger per-span evidence ("whole declaration") — byte-bound and hostile to the
  pack budget.

## 10. Known defects left open by this audit

1. `traced` cannot yet be joined to the pool (select traces the widened unit), and
   `finish()` backfills `rejected_items` for unexamined units. Instrumentation fix
   is scoped but **not** completed here; the regression asserted in §7.3 does not
   exist yet. Until then, any trace-derived number is UNVERIFIED.
2. `hybrid_byte_bounded` in the harness still sizes entity ranges; the harness
   needs the snippet-unit arm before it can serve as the §7 baseline.
3. Cumulative tool-content bytes (≤64 KiB per `REPORT-CONTRACT.md`) are not
   measured at all.
