# M3.3 — Native finishing feasibility (no implementation)

**Status: feasibility only. No native source changed here. No measure beyond already-collected evidence.**

Goal: reduce CPU/RAM of native `optimize()` per write when collections are large, without
changing on-disk format or ABI unless explicitly approved.

## A. Root-cause evidence (collected)

1. **HNSW is already incrementally reused**, not rebuilt:
   - Production/research log: `Reusing first indexer as merge base. field[embedding] … tail_indexers[1]`,
     followed by `End brute force reduce. cost time: [0]s`. (`segment_helper.cc:817-857`,
     `mixed_streamer_reducer.cc:206-315` appends at `next_id = provider->count()`.)
2. **The whole-collection O(N) term is forward + FTS, not HNSW.**
   - On a clean fixture (`dim 256`, 160k rows), per-update `optimize()` wall time was
     ~2.1 s for `dim=256` vs ~1.9 s for `dim=16`; at 300k `dim=32` it was 3.17 s — the bulk
     is independent of vector size, ruling HNSW rebuild out as the dominant term.
   - Phase timestamps (`segment_helper.cc:98` `ExecuteCompactTask`) at 160k:
     - `Compacted scalar and scalar index`: ~0.1–0.9 s
     - `Compacted vector index` (HNSW reuse): < 1 s, `[0]s`
     - `FtsRocksdbReducer: collect_effective_stats` … `reduce done` … `Compacted fts index`: ~1 s at 160k, ~2 s at 160k dim256 (integer-second granularity); `fts_rocksdb_reducer.cc:196-226`.
3. **Scaling** (`native_paired_benchmark`, 8k→160k rows, dim 256): 214 ms → 5 204 ms; roughly
   super-linear once cache pressure begins. Production `fragments` = 1 001 MB → 5 204 ms × 4.18 ≈
   21.8 s (matches observed 18.77/20.46/26.02 s). `entities` (no vector) is the only plausible
   secondary.
4. **Algorithm A (forward base-reuse + tail-append, no format change)**: correctness PASS,
   performance marginal (20–35 % CPU, ~6 % wall) and **not promoted** (storage/peak RAM non-win
   and block accumulation). Source still present, env-gated
   `ZVEC_RESEARCH_SCALAR_REUSE`. See `m1-handoff.md` Gate 2.3 and the M3.2 design doc.
5. **Idle optimize is a no-op** (≈ 7 ms) for every collection on the persisted copy — the
   cost is entirely on the write/finalize path.
6. **`merge_segments_ = false` rejected as default** (segment proliferation: RAM, query fan-out,
   storage). `build_compact_task` default `merge_segments_ = true` (collection.cc:1112).

## B. Code-path / structure facts

- `collection.cc:913-1107` `optimize`: seal writing segment; Phase 1 snapshot under write lock;
  Phase 2 `build_compact_task` → `execute_compact_task`; Phase 3 short exclusive commit via
  `version_manager_`. Inputs are removed and outputs opened.
- `segment_helper.cc:111` `ReduceScalar`: forward writer (Arrow IPC/Parquet) + INVERT RocksDB;
  `:174` `ReduceScalarIndex` per row.
- `segment_helper.cc:635` `ReduceVectorIndex`: reuse base + append tail (incremental).
- `segment_helper.cc:1021` `ReduceFts`: creates a fresh FTS RocksDB, feeds all segments,
  `FtsRocksdbReducer::reduce` multi-way merges all postings/positions and rewrites stat CF.
- `segment.cc` `load_scalar_index_blocks(false)` opens **only the first** SCALAR_INDEX block;
  multiple SCALAR forward blocks are already handled by scan/fetch (`supports multi-block`).
  The INVERT index is therefore a single contiguous DB post-seal — that's why it cannot be
  appended.
- FTS is stored as an immutable BitPacked `RocksDB` with per-block `BM25 max_score` stored
  IDF-weighted (`fts_column/posting/bitpacked_posting_list.cc:183-291,698`). The WAND candidate
  path reads `info.block_max_score` (`fts_conjunction_iterator.cc`).
- `InvertedColumnIndexer::insert` returns `PermissionDenied` on `read_only_`, which `open()`
  sets from the persisted `key_sealed()` (util.cc:115-125). `seal()` writes the marker and
  converts postings to immutable format (`write.cc:454-461`); there is **no unseal**.

## D. Incremental options — evaluation

### D1 Incremental SCALAR/INVERT reuse — not feasible on the current format alone

- Why it fails today: the base's scalar index is already **sealed** and in (immutable) BitPacked form; `insert` rejects writes; no unseal; reopening won't append.
- Two candidate sub-variants:
  - (a) _copy_ the base index, **unseal**, insert tail, **reseal** (regenerating range stats).
    Verdict: risky — appending mutable entries into an immutable-format file risks mixed formats; CF merge operator (=RocksDB level) would post-natively reconcile but query-time stats (range stats for the block-level index) go stale; needs a compatibility test under GC/unseal we can't verify from the current private API.
  - (b) purely in-place, scan and rewrite: O(N) documents → no improvement.
- Cost: O(Δ) in the best case but only with a (now tasks) schema + filter safe subset of fields.
- Delete/update: unchanged (purge ratio handling preserved).
- **Conclusion:** no safe feasibility within the current sealed-index format. **Requires a format/ABI change** to make a sealed index appendable / unsealable.

### D2 FTS incremental reuse — **infeasible within the current FTS format**

- Evidence: `bitpacked_posting_list.cc:183-230,277,291,698` stores IDF-weighted block bounds; reusing base postings after corpus growth **underestimates** the bound (IDF grows with corpus size) and can cause **WAND-driven recall loss**; recomputing is O(N) rewrite → no win.
- To make it incremental would require changing the stored per-block bound to be **stat-independent** (store `max_tf` + `min_dl`, compute bound at query time from `idf_current`). This is exactly the design in `m3.3-feasibility` pending approval and needs: format-version bump, migration/reindex, and a re-validation of per-term block_max_score.
- **Conclusion:** GO only together with a format-change approval.

### D3 Whole-collection merge-frequency reduction — already done partially

- M3-A removed non-essential optimizes (metadata-only, repeated finalize, etc.). Further gains come only from choosing merge grouping that keeps a bounded count **without** fan-out — a.k.a. D4.
- Risks: stale pruning beyond the current 0.3 delete ratio; more persistence latency at commit.

### D4 Bounded segment fan-out (`merge_segments_ = false` / `ResearchMaxSegments`) — **NO-GO as default**

- Rejected by design: storage 1.5×–8×, RSS 1×–2.3×, query p50 2–4× at N≥4 (Gate 2.2 measurement).
- Keep as research-only env gate; explicit operator opt-in only.

### D5 Resource governance / admission (the low-scope lever)

- What exists: 32 MiB/staged 128-row batch budget, 512 MiB staging quota, 8 MiB whole-source admission for non-streamable / >8MB, independent per-collection finalization, frequency gates.
- What is still missing: governor visibility for native `optimize()` peak RSS (process-wide only, not per-collection), and no throttle on *frequency* of native finalizations when mutation rate is high (each finalize is O(collection)).
- Recommendation: add a per-collection dirty-ratio hysteresis (only optimize when vector completeness is already lost or delete ratio above 0.3 AND >20% rows) — already mostly there; check engine-side `has_fragment_deletions` / `has_entity_changes`. Long-term benefit small.

## E. Options worth a prototype (max 2, design-only)

Per the user direction, the direction of least scope prospers over only-FTS
bounds / storage-engine rewrites.

### E preferred — Option X: decouple native optimize from active search (NO new DB engine)

**The most aligned prototype with the original engineering goal** (zg still indexes correctly **but no machine jitter while you code**). Prototype 1 already contains this as a scheduling refinement; here it's the **primary design**, not an algorithm rewrite.

- Work philosophy: keep `Collection::optimize()` (the native full merge) as the required
  correctness mechanism; remove **its disturbance during active coding** via governor
  scheduling in the daemon, not by re-engineering Zvec.
- Already-deployed, free levers: 750 ms/5 s Watch coalescing, `merge_segments_=true`
  (purging), forward/HNSW base reuse, and per-collection finalization (`has_X` gates).
- Additional non-format changes:
  1. Gate finalize on `fragments_incomplete`, `has_fragment_deletions` so a no-deletes/all-complete
     commit (M3-A) never reaches native `optimize()`.
  2. Add a 5–10 s deferral when there is recent user activity (search/watch submission TTL,
     max 3 deferrals then force), to ensure completion.
  3. Cap the daemon's native optimize threads at `min(nproc/2, 4)` via the existing
     `ZVEC_GREP_NATIVE_THREADS` knob (already exposed), applied only during finalize (dev work).
  4. Per-collection dirty ratio ≥20% gate (already mostly there; promote to explicit rule).
  5. Surface `index storage finalization` micros + RSS as first-class telemetry so user/config
     can see the native cost without a benchmark campaign.
- Boundary: no format change, no schema change, no `merge_segments_ = false`, no HNSW params,
  no M6 memory ceiling. Effect on user-observable desktop latency is the exit criterion.
- Exit criterion (example): search p95 during finalize ≤1.25× idle, and `optimize byte-count` reduces
  by ≥15% at 1k-file scale with no storage regression >2 %.
- Risk: deferral lengthens the collection's tombstone/debt accumulation window; must hard-cap
  (force finalize) so this never grows without bound.

### Prototype 1 — governance dirty-ratio refinement (GO for design, not implementation)

- Algorithm: extend M3-A per-collection finalization hysteresis — `fragments_incomplete == false
  && delete_ratio < 0.3 && has_entity_changes == false` → skip native `optimize()` entirely.
- Code paths: `storage/store/mod.rs::finalize_writes`, `IncrementalPlan` bitflags; **no native
  touch**.
- Preserves vector completeness safety probe; on-disk format unchanged.
- Exit criterion: ≥15% fewer native optimize byte-count at 1k-file scale without regressing
  `search latency` or storage by >2%.

### Prototype 2 — stat-independent FTS block bound (NO-GO pending full design approval)

**NO-GO until a complete incremental-FTS design exists — not only BM25 bounds.** Supporting topics
not yet specified that must exist before Gate-2 implementation:

1. Reuse model: base vs. tail postings, doc_id remapping, whether `FtsColumnIndexer` can operate as
   mutable multi-block store (single immutable RocksDB vs. delta-tail persisted separately).
2. Update: inverted-list merge, tokenization cost on append vs. full rebuild.
3. Delete/tombstone: `delete_row_id_bitmap` against reused postings, doc-max_score staleness.
4. Reopen/multi-open recovery from a partially appended immutable RocksDB + stat CF, seal markers,

5. Crash recovery: WAL, manifest, generation, `collection.cc:994` temp-dir GC.
6. Migration / compatibility with existing sealed postings dirs and old binaries.
7. Memory & CPU bound proof (per-block `scorer_` / `merge` peak) with real capping.
8. Correctness oracle: exact FTS top-k recall + WAND pruning regression test.

Costs (format-version bump, reindex of every local index, maintenance burden on
`bitpacked_posting_list.cc` / `fts_column_indexer.cc` / `fts_rocksdb_reducer.cc` / WAND path

advantages. **Prototype 2 should only be promoted if** the governance/Option X diff measurement is
insufficient (per the R3 "M3.3 trigger" evidence) AND this full design is written and approved.
No implementation in this gate.

## H. Corrections from user review (2026-10-16, round 3)

The user's four questions directly challenge three claims I made; re-based answers below
(see relevant evidence above and in `m1-handoff.md`).

### H.1 Search completeness when skipping one optimize is NOT guaranteed

Claims in §A.4/§E ("HNSW is not rebuilt by Hessian reuse, so no false negatives from skipping")
are partially false. The actual safety story:

- Data stays queryable across multi-segment forward + FTS + vector (HNSW ANN is an
  approximate nearest-neighbor index; ranking depends on segment layout — there is no "no
  false negatives" guarantee in an ANN regime).
- `completeness=0` is the `M3-A` safety predicate for "needs finalize" — deferring a
  required gap leaves the visibility contract intact in *availability* terms
  (`NotIndexed` fail-closed per Gate 1) but not in *latency/recall-freshness* terms.
- **No more "skip one optimize is harmless to search" statement should be made.**
  `merge_segments_=false` path (= bounded fan-out) was measured Gate 2.2: query p95 2–4×.
- Until tested against a real multi-fragment corpus, `optimizing on skip` means "unknown
  recall/latency penalty" — treat as potentially correctness-affecting, not cosmetic.

### H.2 `nice(19)` is NOT provably safe

`setpriority(PRIO_PROCESS, 0, 19)` only affects the calling Linux thread, not Zvec's worker
pool. Raise/release asymmetry means a process can raise from 0 to 19 but not decrease reliably
without suitable privileges. Naive instrumentation would leave unrelated work stuck at
low priority. **Do not implement** until Native worker ownership/lifecycle is mapped. Derive:
- native threads are capped by `ZVEC_GREP_NATIVE_THREADS` env (already available);
- priority knob stays out of scope.

### H.3 Frequency-vs-priority reduction: hypotheses, not measured results

- Fewer optimize calls can be achieved via scheduling (Option X) but only when edits are
  clustered; the evidence is 30 burst → 1 job, single file → one 2.1 s.
- Lowering priority gives at most 10–30% jitter drop under core contention. Both figures
  unmeasured vs a comparable daemon. Capability<|constrain|>scenario vs priority requires a controlled
  benchmark, not inference.

### H.4 Which is bigger for desktop?

- *Frequency reduction* of the larger lever: it directly removes full-merge *runs*, which
  is what causes multi-second freezes. Option X can suppress an optimize run only when
  fragments are already complete + no deletes pending; for real edits, they will be deferred
  5–10 s at most, then run
- *Priority tuning* only smooths *interference*; it cannot stop a 2–7 s optimize from
  holding CPU that heavy workload needs. Use it as a complement, not a substitute.
- Neither reduces per-write cost; both are latency/perceived-smoothness.
- The **only** O(collection) cost reducer that survived evaluation: **none currently safe**
  (Algorithm A ~6% wall; segment fan-out regressed query; stat-independent FTS format change
  requires bump+migration; Algorithm A rejected for INVERT sealed blocker).
- So: recommend Option X for the user-visible stutter case, but explicitly ceil it at
  "doesn't reduce the underlying merge cost" — open **M3.3** only if sustained production
  observation shows real degradation past the thresholds.

### H.5 Closure discipline
- Do not present deferral/priority as measured improvement without numbers. Every win must
  be stated as measured-hypothesis vs simulation, tagged.

## J. M3.3 QoS feasibility — thread topology, scheduling boundary, impact evidence

No implementation. Design-only. Sources used are `segment_helper.cc` + the C API
already reviewed in A-G.

### Focus 1 — thread topology

- `Collection::optimize()` starts in the caller's thread (Phase 1 seal under write lock,
  then releases). Phase 2 `ExecuteCompactTask` uses two distinct pools defined in
  zvec `GlobalResource`:
  - **query_thread_pool** — created from `GlobalConfig::query_thread_count()`.
  - **optimize_thread_pool** — created from `GlobalConfig::optimize_thread_count()`.
- The Rust side (`rust/src/storage/zvec.rs`) only sets `num_threads(...)` which maps to
  Zvec's **query** thread count. The optimize pool is set via the C API
  `zvec_config_data_set_optimize_thread_count`, which `zvec-rust 0.7.2` does **not**
  expose. So in a 2-thread baseline (`ZVEC_GREP_NATIVE_THREADS=2`), the native build
  runs its optimize's HNSW/FTS/vector merge on its own default pool (likely `nproc/2`
  to `nproc`), **not** capped by the query budget.
- `SegmentHelper::ReduceVectorIndex` calls `merge_options.pool =
  GlobalResource::Instance().optimize_thread_pool()` when concurrency == 0 — so the
  optimize pool is the actual executor.
- **Conclusion:** optimize threads are an **independent, larger pool** than query threads.
  They are *not* auto-capped at the `--native-threads` level. This is a measurable
  source-confirmed fact (`global_resource.h:24-33, global_resource.cc:20-30`).

### Focus 2 — scheduling boundary / tradable priorities

- Native optimize's thread pool is **a separate pool**, so in principle a priority
  change inside the optimize pool would not directly touch search threads — at least
  within zvec's design. **But** our process-level tools cannot reach threads owned by
  `GlobalResource` (no public enumerate-API in the C ABI).
- `setpriority(PRIO_PROCESS, 0, 19)` affects every thread of the process. That leaves
  search workers at `nice=19` permanently once raised (unless reset) — matches the user's
  correction.
- Thread-count cap (`optimize_concurrency` param passed to each task, or the pool size)
  is the **only** clean knob exposed by `MergeWithOptionalReuse`. Setting
  `ZVEC_RESEARCH_OPT_THREAD_CAP=N` at native would be well-contained — but that is a
  *native research flag, not yet code*. Without native change, the Rust-side lever is only
  `ZVEC_GREP_NATIVE_THREADS`, which only affects the query pool (minor at best).
- **Conclusion:** safe hardware isolation is **not available** without either (a)
  `GlobalConfig::optimize_thread_count()` exposure in `zvec-rust`, or (b) a small
  native change. Per-thread nice tricks are **NO-GO** pending thread-ownership mapping.

### GO / NO-GO verdicts per focus area

1. **Thread topology:** source-confirmed (separate optimize thread pool exists but pool entry
   is private). **NO-GO** for OS-level process-wide scheduling; **GO (design-only)**
   for capping the optimizer pool if `zvec-rust` exposes a setter or the daemon side calls
   `zvec_config_data_set_optimize_thread_count` directly.
2. **Scheduling boundary:** per-thread isolation is **not safely available** without a native path.
   The pure-daemon deferral (Focus 0 Option X) is available and safe (only gate entry points).

3. **Impact evidence:** evidence is suggestive but not a closed loop (query p95 not co-measured

### Combined verdict
- If boundary cannot be cleanly addressed, the realistic answer is: **none of the three options
  alone (frequency, priority, devolved) genuinely reduces the O(N) native finalize** — they only
  redistribute. So the only potentially GENUINELY useful direction under the strict "no native
  format/API" red line is being warmer `merge_segments_=false`/Algorithm A with its measured
  counter-arguments (query/regression). None reduce CPU per update while honoring all existing

- Keep monitoring the *actual* production workload (RSS, `fragments_optimize_micros`, p95) per the
  original R3 criteria. If sustained >30s / >2×-RSS is recorded, M3.3 has the source evidence it
  needs (§A–G already existing) and a concrete design track (Prototype 1). Otherwise, leave.

## J. M3.3 QoS feasibility — thread topology, scheduling boundary, impact (no implementation)

### J.1 Thread topology (source-confirmed)

- Native `optimize()` runs in the caller's thread for the lock/Phase-1 part and dispatches the heavy Phase-2 (`execute_compact_task` → `ReduceScalar`, `ReduceVectorIndex`, `ReduceFts`, `filter record batch`) on Zvec's *independent* optimizer thread pool, distinct from the query/reader thread pool.
  - Evidence: `global_resource.h:24-33` (`query_thread_pool()` and `optimize_thread_pool()` are separate `std::unique_ptr<ailego::ThreadPool>`), `global_resource.cc:24-29` (`GlobalConfig::query_thread_count()` vs `optimize_thread_count()`). `segment_helper.cc:804-809` passes `optimize_thread_pool()` to `MergeWithOptionalReuse(...)`; `Index::merge` invokes `add_vec` workers there.
  - `collection.cc:2029` does use the **query** pool in user code (task-packaging threads), not the optimizer pool.
  - The Rust side only configures `num_threads(...)` in `rust/storage/zvec.rs:29-44`, which maps to the query pool. There is no Rust call to `zvec_config_data_set_optimize_thread_count` observed.
- Conclusion: native optimize uses its **own worker set**, separate from search query threads **unless** they share upstream isolation in the daemon (sharing) is implementation-dependent.

### J.2 Scheduling boundary — can optimizer threads be safely deprioritized?

- **Process-wide `setpriority(PRIO_PROCESS, 0, 19)` is NO-GO.** It affects every thread in the process (search, embedding, tokenizer) and is subject to privilege asymmetry (raise 0→19 allowed; lowering back requires privilege), per the user's correction. Do not implement before worker ownership and lifecycle are mapped end-to-end.
- **Per-thread `PRIO_THREAD` is NO-GO without C++ changes.** `GlobalResource` does not expose thread TIDs; `optimize_thread_pool` task lifecycle cannot be safely handed to Rust. Touching Native worker ownership is out of scope.
- **Only safe knob without a Native ABI change:** cap the optimizer pool size via `ZVEC_GREP_NATIVE_THREADS` env (already supported, default 2) if the build exposes `zvec_config_data_set_optimize_thread_count`. Rust does not currently call it, so this remains a proposal, not an implemented lever.
- **Scheduling deferral in the daemon (Option X)** stays **GO for design**, but as a **governance deferral** only: do not claim it chops the *measured* CPU wall (it does not), only redistributes finalize calls and search-p95 interference.
