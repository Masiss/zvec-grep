# M3.2 — Incremental native index maintenance — design review (2026-10-16)

**Status: DESIGN for review. No native source changed. Nothing applied to production. Awaiting approval before any native edit.**

Scope requested: reduce the full-collection merge cost when a small mutation happens, without
segment-only storage, query fan-out, or HNSW-parameter changes, and without a new storage
architecture. This document reads the actual native source and reports what is already
incremental, what still dominates, and the safest feasible slice.

---

## 0. Corrected diagnosis (this supersedes the Gate 2.3 wording)

The M3 premise was "a small vector add forces a full-collection **HNSW** merge". Direct source
reading and phase-level measurement show that is **not** what happens today:

1. **The HNSW graph is already reused incrementally.** On the non-purge merge path the vector
   reducer copies the largest input segment's index file and appends only the *other* segments'
   vectors:
   `segment_helper.cc:817` `CanReuseFirstIndexer` → `:824` `FileHelper::CopyFile` →
   `:827` open in place → `:831` `vector_indexer->merge(tail…)`. Runtime log:
   `Reusing first indexer as merge base. field[embedding] … tail_indexers[1]` followed by
   `End brute force reduce. cost time: [0]s`. The reducer reads **only** the fed (tail)
   streamers and appends at `next_id = provider->count()` (`mixed_streamer_reducer.cc:242-286`),
   so the reused base graph is not re-added.
2. **The per-optimize O(collection) cost is dominated by the non-vector reducers** —
   `ReduceScalar` (forward rows + INVERT index) and `ReduceFts` (FTS postings). Both reprocess
   **every** input row/posting on every optimize.

Measurement (isolated `native_paired_benchmark`, dim 256, base 160 000, 1 upsert+flush+optimize):

| dimension | update p50 | update CPU | peak RSS | bytes written |
|---:|---:|---:|---:|---:|
| 16  | 1 856 ms | 2.58 s | 974 MB | 88.5 MB |
| 256 | 2 069 ms | 2.93 s | 1 382 MB | 243 MB |

A 16× increase in vector size changes time by ~11% and CPU by ~14%; the O(N) floor is
independent of the vector index. Phase log at 160 k, dim 256: `Compacted scalar and scalar index`
and `Compacted vector index` complete in well under a second; `FtsRocksdbReducer` spans the
remaining ~1 s while walking `effective_docs[160001] effective_tokens[…1.6M]`. Scaling the text
20× (1.6 M → 32 M tokens) moved the update only +15% (fixed distinct-term set), confirming the
FTS cost is driven by the full-corpus posting merge, not raw token count.

**Conclusion:** priority (1) "reuse / update the completed HNSW graph" is **already implemented**.
The remaining lever is to make the **forward/inverted** and **FTS** reducers reuse the unchanged
base instead of rebuilding it. Both are pure data (no scoring on the forward path), so the design
is about structural reuse, exactly priority (2).

## 1. Where the time goes — merged-segment dataflow

`Collection::optimize` (`collection.cc:913`) → seal writing segment → `build_compact_task`
(`collection.cc:1112`) → default grouping: one `CompactTask` over all persisted segments
(`max_doc_count_per_segment = 10_000_000` ≫ production rows, so everything groups into one).

`SegmentHelper::ExecuteCompactTask` (`segment_helper.cc:98`) then, into a fresh temp segment dir:

1. `ReduceScalar` (`:174`) — streams **all** rows through `ForwardWriter` (Arrow IPC/Parquet) and
   rebuilds the INVERT index (`InvertedIndexer`). **O(total rows).**
2. `ReduceVectorIndex` (`:635`) — HNSW: reuse base + append tail (already incremental). Minor.
3. `ReduceFts` (`:1021`) — creates a new FTS RocksDB and feeds **all** segments into
   `FtsRocksdbReducer`, which multi-way merges **all** postings/positions. **O(total tokens).**
4. Commit (`collection.cc:1002-1076`): new segment committed through `version_manager_`
   (manifest), inputs retired. Crash safety: temp dirs are not referenced by any manifest and are
   discarded on crash (comment `collection.cc:994`).

The invariant that makes base reuse possible already exists for vectors: merged rows keep their
**global doc ids** (base ids first, tail ids appended at `next_id`), so no id remap is needed.

## 2. Algorithm A — "base-reuse + delta-append" for forward & inverted (no format change)

Generalize the existing HNSW reuse pattern to the forward block and the INVERT index.

**Mechanism (non-purge case, i.e. delete-ratio ≤ 0.3 → `task.filter_ == nullptr`):**
1. Choose the largest input segment as base (largest `doc_count`).
2. Copy its forward block file and INVERT RocksDB into the new temp segment dir
   (exactly what `MergeWithOptionalReuse` does for the vector index).
3. Append only the tail segments' rows: forward rows written as a **delta block** with global doc
   ids continuing after the base; INVERT postings written via the existing RocksDB merge operator
   (`InvertedIndexer`), term keys unchanged, doc ids already global.

**Code paths / structures to touch**
- `SegmentHelper::ReduceScalar` (`segment_helper.cc:174`) — split base vs tail; emit base block
  (copy) + delta block; skip re-serialization of base rows.
- `ForwardWriter` (`db/index/storage/forward_writer.h`) — content copy + delta append; or a
  `CopyFile` of the base block + a new IPC file for the tail.
- `InvertedIndexer` (`db/index/column/inverted_column/`) — reuse base DB + `Put` merge for tail.
- Segment block model — already a vector: `SegmentMeta::persisted_blocks` / `persist_stores_`
  (`meta.h`, `segment.cc:371,514-562`). Verify scan unions multiple SCALAR blocks in ascending
  doc-id order.
- `SegmentHelper::ExecuteCompactTask` (`:98`) — build the base/delta split and block metadata.
- `FileHelper::CopyFile` (already used by the vector path).

**insert / update / delete / tombstones**
- Appends keep global doc ids (base range then tail range). Upserts of an existing pk write a new
  tail row; the old row is a tombstone but stays physically present on the non-purge path (the
  existing code already preserves deleted rows for non-purge, `collection.cc:1225-1229`), so the
  base copy is byte-valid.
- **Purge path (delete-ratio > 0.3)** falls back to the current full rebuild with delete-row
  filtering. This preserves tombstone reclamation.

**Query visibility, FTS, filters, recall**
- Forward + INVERT carry raw data only — no score bounds — so results are exact; no recall change.
- Filters (`file_id`, path, etc.) are applied on the forward reader across blocks; unchanged.
- FTS is untouched by Algorithm A.

**on-disk format / C API**
- **No format change and no C API change if** the segment may hold two SCALAR/inverted blocks
  (the model already stores `persisted_blocks` as a vector and opens one store per block). If any
  reader assumes a single forward block, the change is a read-only union in `segment.cc`.

**Restart / crash recovery**
- Unchanged: the merged segment is committed atomically through `version_manager_`
  (`collection.cc:1022-1043`); temp dirs are discarded on crash.

**Cost**
- CPU: O(delta) serialization instead of O(N).
- Peak memory: one forward batch + tail indexer.
- Disk writes: base block **copy** is O(base) I/O unless base files are referenced
  (copy-on-write across segments — out of scope, see §5); delta O(delta). INVERT merge stays
  O(N) unless the base DB is copied and tail appended.
- Complexity: medium; isolated to the scalar/forward path; no scoring risk.

**Invariants preserved:** global doc-id contiguity, forward order, INVERT semantics, tombstone
handling, manifest/version commit, reopen correctness.
**Not guaranteed:** elimination of the O(base) disk copy (Algorithm A reduces CPU, not the base
I/O, without cross-segment COW).

## 3. Algorithm B — incremental FTS (requires an on-disk FTS format change)

**Why the obvious reuse is unsafe (blocker with source evidence).**
The BitPacked posting list embeds a per-block BM25 bound computed **with IDF** at build time:
`posting/bitpacked_posting_list.cc:190,203-230` computes `max_score` via
`scorer.score(df, tf, doc_len)` and stores it (`:277`, `:291`); the decoder reads it back
(`:698`) for WAND block skipping (`iterator/fts_conjunction_iterator.cc:103-137`,
`fts_candidate_iterator.h:46`). The reducer writes these bounds "consistent with the values
flushed to stat_cf" (`fts_rocksdb_reducer.cc:198,226`).

When the corpus grows, `N` increases and every term's `IDF` **increases**
(`BM25Scorer::idf`, `bm25_scorer.cc`), so the previously stored block bound is now **too low**.
A too-low bound makes WAND prune candidates that can still reach the top-k → **silent recall
loss**. Therefore reusing base postings is safe **only if the block bounds are recomputed**, which
is an O(N) rewrite — i.e. no win within the current format.

**Proposal.** Make the stored per-block bound **stat-independent**: store the per-block
`max_tf` and `min_dl` (or equivalent raw components) instead of the IDF-weighted score, and
compute the bound at query time as `idf_current(df) · score(max_tf, min_dl)`. The code already has
both pieces (`fts_column_indexer.cc:349` `max_score_bound(df)`, and the max-tf path `:350-360`).
Then base postings stay valid as the corpus grows and the merge becomes base-reuse + tail append.

**Code paths:** `FtsRocksdbReducer` (`fts_rocksdb_reducer.cc`), `BitPackedPostingList`
encode/decode (`posting/bitpacked_posting_list.cc`), `FtsColumnIndexer::create_term_iterator_from_raw`
(`fts_column_indexer.cc:345-364`), `SegmentHelper::ReduceFts` (`segment_helper.cc:1021`).

**insert/update/delete:** tail postings appended with global doc ids inside the copied base
RocksDB; `stat_cf` updated to base+tail (docs, tokens); purge path unchanged.
**Query visibility / filters / recall:** preserved — bounds remain valid for any `df`/`N`.
**on-disk format:** **CHANGES** (per-block stored quantity) → format-version bump and a
migration or reindex of existing collections. **Not covered by the current "no format change"
constraint.**
**Cost:** CPU O(delta), memory O(one batch), disk O(base copy + delta).
**Complexity:** high; requires scoring re-validation (exactness fuzz vs a full reduce).

## 4. Design decision and first implementation slice

### 4.1 Implementation slice A (2026-10-16, research-only, flag default OFF)

Implemented on the research checkout `.local/native/zvec-native-profile`, gated behind
`ZVEC_RESEARCH_SCALAR_REUSE` (unset/`0` = byte-for-byte original behavior):

- `src/db/index/segment/segment_helper.cc` — `SegmentHelper::ReduceScalar` gained a
  `collection_path` parameter and a fast-path branch (`ReduceScalarReuse`) taken only when the
  flag is on, `filter == nullptr` (non-purge), and there are ≥2 input segments.
- **Forward reuse:** every SCALAR block of the first (smallest `min_doc_id`) input segment is
  byte-copied into the output segment with fresh local block ids, preserving order; only the tail
  segments' rows are appended as a new delta SCALAR block. This keeps the copied blocks as the
  local-row prefix, so no doc-id remap is needed (the same invariant the HNSW reuse relies on).
- Preconditions (any unmet → fall back to the full reduce): each base SCALAR block must contain
  every reduced column; segment doc-id ranges must be strictly increasing and non-overlapping;
  base must be non-empty.
- **Scalar (INVERT) index:** the base index is **sealed**, so it cannot be appended in place (see
  4.2). The fast path therefore rebuilds the scalar index fully from all input rows (the
  `ReduceScalarIndex` fallback) while still reusing the base forward block.

### 4.2 Blocker — the base scalar index cannot be reused

`InvertedColumnIndexer::open` sets `sealed_ = true` **and** `read_only_ = true` whenever the
per-indexer `key_sealed` marker is present
(`inverted_column_indexer_util.cc:116-125`); `insert` returns `PermissionDenied` when
`read_only_` (`inverted_column_indexer_write.cc:24-26`); and `seal()` both records the marker and
converts postings to the immutable BitPacked form
(`inverted_column_indexer_write.cc:436-461`, `...generate_statistical_indexes`). There is **no
`unseal`** entry point. Appending the tail into a copied sealed base is therefore unsafe (mixed
mutable/immutable postings + stale range statistics), so the slice keeps the full
`ReduceScalarIndex` rebuild as the fallback, exactly as the task allowed. The measured effect of
slice A is thus limited to the forward-block serialization; the scalar-index rebuild remains
O(collection).

### 4.3 Verification

- `native_scalar_reuse` (new, ignored): base insert → tail insert → repeated optimize →
  update → delete, with forward-field and INVERT-filter assertions before and after a
  read-only reopen. **Passes with the flag OFF and ON**, and the ON run logs
  `ReduceScalar reuse applied` (positive confirmation the fast path ran). The test's
  read-only reopen confirms the two-SCALAR-block segment round-trips the manifest.
- `cargo test -p zg-engine --lib` against the rebuilt library: **526 passed, 0 failed, 11
  ignored** both with the flag OFF (baseline) and ON.

### 4.4 Remaining decision

Algorithm B (incremental FTS) is unchanged and still needs a format change. Algorithm A's
forward reuse is correct but partial; promotion depends on the paired measurement below.

### 4.5 Paired measurement (dim 256, base 48k/160k, 5 updates, single index)

`native_paired_benchmark`, `BENCH_SINGLE_ONLY=1`, 3 repeats per cell (median shown). The
benchmark schema has FTS + vector but **no INVERT** field, so this isolates the forward-reuse
effect (the store collections additionally carry INVERT and fall back to a full scalar rebuild).
The host was loaded, so single-run spread is large (e.g. an ON run at 160 k ranged
1961–5633 ms); treat these as order-of-magnitude.

| base | flag | update p50 | update CPU | query p50 | peak PSS | bytes written | live storage |
|---:|---|---:|---:|---:|---:|---:|---:|
| 48 k | off | 944 ms | 7.60 s | 9.0 ms | ~590 MB | ~398 MB | 73.83 MB |
| 48 k | on  | 883 ms | 7.17 s | 9.1 ms | ~599 MB | ~399 MB | 73.83 MB |
| 160 k | off | 3798 ms | 28.05 s | 22.8 ms | ~1.37 GB | ~1223 MB | 240.10 MB |
| 160 k | on  | 3429 ms | 36.97 s | 24.9 ms | ~1.38 GB | ~1224 MB | 240.10 MB |

### 4.6 Decision — do not promote (research-only, flag off)

- At 48 k the win is ~6% (within noise); at 160 k the update p50 is numerically better but the
  **CPU is ~32% worse** and query latency/storage/RSS/writes are unchanged. There is **no
  consistent, material resource improvement** once the dominant terms (FTS reduce and the full
  scalar-index rebuild) are accounted for — the forward-block serialization being saved is a small
  fraction of the merge.
- The fast path never consolidates forward blocks: each reuse merge copies the base blocks and
  appends one delta block, so the SCALAR block count grows with every merge. Over a long-running
  writer this increases fetch/scan fan-out within the segment — a storage/latency liability the
  user's bar explicitly guards against.
- Per the task's rule 7, this implementation stays **research-only with the flag off** and is not
  promoted.

### 4.7 Verdict on Algorithm A

Forward base reuse is **correct** and **behaviour-preserving**, but it does **not** clear the
resource bar: the merge's dominant costs are the FTS reduce and (for real collections) the
scalar-index rebuild, neither of which Algorithm A removes. The next viable lever is Algorithm B
(incremental FTS), which requires an on-disk FTS format change and separate approval; the sealed
scalar index is a hard blocker for incremental INVERT without a format/immutability change.

## 5. Constraints that cannot be guaranteed (honest limits)

- **No in-format algorithm removes the O(N) base I/O entirely.** Copy-on-write across segments
  (reference the base files instead of copying) needs cross-segment reference counting / GC — a
  storage-architecture change, explicitly out of scope. A log-structured single growing segment is
  likewise out of scope.
- **FTS cannot be made incrementally reusable within the current format** (Algorithm B blocker):
  the stored `block_max_score` is IDF-weighted and becomes an invalid WAND bound once the corpus
  grows. This is the single most load-bearing finding; without a format change the FTS reduce
  stays O(total tokens).
- **Segment-only / query fan-out / HNSW-parameter tuning are excluded by direction** and are not
  needed: the vector index is already the cheapest part.
- The above measurements are on an isolated fixture at `dim=256`; production proportions
  (fragments forward/FTS/vector, plus `entities`) should be confirmed with the per-collection
  `index storage finalization` log on a natural job before committing to Algorithm B.
