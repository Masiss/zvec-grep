## Motivation and bounded design

Prior four-writer measurements showed state-lock wait p95 around 9.1–12.9 ms against roughly 0.85–1.03 ms state-lock hold and 0.82–0.98 ms WAL append. Source inspection confirmed that both `Upsert` and `ApplyBatch` serialize through the writer-state mutex across WAL append/fsync. That implicated serialization around synchronous durability but did not isolate scheduler delay from lock wait or fsync.

The research-only `Options::writer_group_commit_max_batch_size` (default 0/off) sends concurrent `Upsert` calls through one per-index worker. The registered profile uses a maximum of four records or 500 µs, with a 6 MiB group-byte bound and 256 KiB per-document admission bound. The queue itself is bounded. Large documents use the ordinary direct path. The worker writes each group through existing `ApplyBatch` WAL framing/replay and publication, preserving ordered durable append and all-or-nothing visibility of each group. `Delete`, explicit `ApplyBatch`, and `Flush` retain their existing paths. Shutdown drains admitted calls without adding an implicit flush.

After the measurement, source review found that queued requests copied each `Document` before waiting for bounded queue admission. The final unmeasured source instead keeps references to the synchronous caller-owned inputs until completion, avoiding an additional copy for arbitrarily many producers waiting outside the admitted queue. The call remains blocked until the worker has copied the mutation into the bounded batch and completed it. This is a memory-safety/resource-bound refinement; it was not included in the measured binary and was not remeasured because the one-operation profile is consumed. The measured binary remains `af4eab…`; the final unmeasured source build is `47f0b531312b2a3353796c79b4f640b72a60abdd3507e0a8cbf0f358340f9cd8`.

The direct arm's large writer tail was predominantly waiting rather than current-thread CPU: maximum measured state-wait CPU was 0.086 ms while state-wait p95 was 54.165 ms. This is consistent with blocking/scheduling behind serialized writes, with fsync also a material part of the held critical section; it does not prove one exclusive cause. The group arm exercised the intended treatment (eight four-record batches) and reduced sync count. Its queue-wait series is specifically pre-dispatch group-formation time, not total time waiting for batch completion; end-to-end writer samples include service and completion.

Reader queries finished early in each arm while the compactor continued for about 15 ms. This operation therefore **does not** answer continuous reader-tail behavior through compaction/GC. ## Next bottleneck: maintenance still owns the writer-state lock

The same operation already exposes a separate, actionable cause of writer tail; no extra telemetry or run is needed to identify it. In the direct arm, concurrent compaction held the state mutex for 15.402 ms (5.313 ms current-thread CPU), with 10.183 ms merge build and 5.043 ms publication. The explicit post-writer flush then held it for 14.583 ms (1.031 ms CPU). Group commit did not shorten those maintenance critical sections: 15.234 ms compaction hold and 14.565 ms flush hold. Per-flush stages varied between arms (for example, direct segment-write 7.263 ms/0.443 ms CPU and manifest-write 5.801 ms/0.221 ms CPU; group segment-write 6.839 ms/0.587 ms CPU and tombstone-write 5.684 ms/0.252 ms CPU). This makes non-CPU wait inside the durable maintenance path plausible, but the shared-host run and unavailable cgroup I/O stats do not establish a specific device/filesystem bottleneck.

Source matches the measurements: `Flush()` keeps the recursive writer-state mutex for all of `FlushInternal`. `FlushInternal` drops the query mutex while building/writing a segment, so readers can continue on the prior visible state, but writers remain excluded; then it reacquires the query mutex for publication, writes stats/tombstones/manifest, resets the WAL, runs GC, and resets the delta before returning. `CompactNow` similarly performs merge work while serialized. Thus group commit targets competing WAL syncs but does not remove the maintenance lock interval. The separately recorded snapshot-rebase prototype reduced compaction state-lock hold to 2.684 ms in one non-policy-matched, performance-ineligible run; that is a candidate mechanism, not a comparable result or winner.

**Next engineering target:** test the combination of ordered group commit and WAL-preserving snapshot rebase, or design a dedicated incremental snapshot-flush protocol. Do not just unlock the state mutex around `FlushInternal`: it currently publishes `manifest.wal_seq = last_wal_seq_` and resets the whole append-only WAL, so concurrent post-snapshot records would need a retained WAL suffix and consistent snapshot/tombstone/stats generations. Any prototype must keep WAL ordering, atomic visibility, replay, and crash recovery intact, with a deterministic writer/read/crash regression before performance measurement. The blocked continuous-reader operation remains separate and must not be retried.

## Resource and evidence limits

- The actual operation's host-before receipt had `MemAvailable=5,820,484 KiB` against the unchanged 5,477,762 KiB historical minimum; disk reserve passed at 59.38 GB available against 18.22 GB.
- The historical load-1 comparison was `5.36 > 3.14` and recorded `FAIL`, but this profile explicitly treats that historical envelope as observation-only (not an admission/abort gate). Host swap was heavily occupied (~14.5 GB); the contained cgroup itself used no swap.
- Cgroup limits: memory 512 MiB, swap 0, CPU `200000 100000`, pids 128. Peak memory was 146,993,152 B (~140 MiB); OOM counters and CPU throttling were zero. Cgroup I/O controller/statistics were unavailable, so no per-arm physical-I/O claim is made. The service reported ~675 ms CPU and 1.105 s runtime.
- Host pre/post process snapshots including RSS/PSS/swap are preserved as `session-host-process-before.json` and `session-host-process-after.json`; the complete operation manifest verifies.
- This is one small, fixed-order run on a shared host with elevated load and high swap occupancy. It cannot establish a stable p95 improvement, CPU saving, reader-tail non-regression, or architecture win. No production defaults were changed.

## Decision and next work

Keep this as a bounded **research-only** option: the one run supports the mechanism (fourfold fewer sync calls and lower observed writer tail under this particular contention envelope), but does not justify enabling it by default. No repeat is authorized by the consumed profile. Continue source-level writer/flush analysis, then return to native flush/compaction and reader contention with a genuinely distinct profile only after fresh unchanged preflight gates. Preserve the failed continuous-reader operation and do not claim its latency.

The final reference-based queue change passed TSan; the one-operation benchmark remains consumed and was not rerun after that source-only memory refinement.
