## Interpretation and next work

This one small, single-arm run shows near-zero M4 query-lock waiting for this 64-document workload and the requested reader/writer/GC distributions. It does **not** compare against the old exclusive-lock implementation, estimate stable p95, establish a performance win, or prove behavior under larger collections/write backlogs. Do not compare its latency directly with earlier 500×5 results; workloads and code versions differ. Writer commit latency includes native flush work; no claim that the M4 state mutex causes that tail is supported. The result argues against making another lock change based on this measurement alone. Keep the writer-preferred lock and durability/correctness prototype unpromoted; next useful work is source-level attribution of the writer-side M4 state-lock hold and a separately bounded, appropriately contained diagnostic only if it can isolate that cause without changing the hard gates. No production changes or pushes.

The operation plan, exact command, host/cgroup/watchdog telemetry, workload samples, cleanup receipts and `SHA256SUMS.txt` are retained under `20261022/m4-lock-contention-microbench-20261022-042253-3aa79d/`. The initial 256 MiB abort is retained under its own operation root.

This avoids one owned vector/allocation per emitted posting and keeps scratch proportional to a block rather than a merged term. ## Compaction writer-serialization boundary

**Baseline confirmed in source:** ordinary `CompactNow()` still holds the state `mutex_` through `MergeRuns`; `MergeRuns` releases only `query_guard` while it streams and reopens the replacement run. The existing bridge barrier confirms readers finish during that build while a competing `Upsert` remains queued until publication; the bridge/crash suite passes 4,661 checks with 0 failures. This is correctness evidence, not a writer-latency measurement.

**Owner-authorized prototype implemented:** `Index::CompactNowSnapshotPrototype()` is a separate opt-in path; the default API and storage format are unchanged. It pins immutable runs, copies tombstone IDs within selected input-run ranges (IDs in range gaps are harmless to the merge), and charges the run-metadata/tombstone snapshot conservatively against the compaction budget before allocation. It reserves a run ID, releases both state and query locks for the streaming build, then reacquires them in state→query order. Publication requires unchanged `state_generation_`, `last_wal_seq_`, reserved run sequence, and run IDs/files/segment identities. Concurrent mutations or flushes invalidate the snapshot; the output is removed and an error returned without publishing the stale manifest. WAL-sequence comparison also catches failed/incomplete writer attempts that may not have changed query state. A per-index try-lock bounds merge builds; automatic maintenance defers while the prototype is active, and overlapping explicit prototype calls fail before building. Run-ID gaps after a conflict are avoided when no later allocation used the reservation; gaps remain harmless if a concurrent flush advanced the sequence. The concurrent-flush regression exposed a GC race: `GarbageCollect()` treated the active `run-N.seg.tmp.<pid>` file as an orphan and removed it during the merge. `MergeRuns` now registers both active temp and final filenames under the state lock, and GC preserves them until the build commits or cleans up; the test also enables forced rebuild-on-flush to prove that optional maintenance defers instead of failing the durable flush.

**Verification:** Final `m4_correctness` passes 18,931 checks with 0 failures, including deterministic delete and upsert+flush during the merge; stale merges are rejected and their outputs removed without losing the writer's reserved run ID, a later stable merge commits and survives reopen, a second overlapping build is rejected, snapshot-budget preflight refuses without changing searchable state, and pre/post-manifest faults recover to the expected old/new manifest. ThreadSanitizer passes the same 18,931-check suite with 0 failures and no race report. The final-tree eight-target CTest suite passes 8/8; bridge/crash passes 4,661 checks with 0 failures. LSP diagnostics are clean for all five changed C++ paths after retrying one timed-out file. No benchmark has been run for this prototype; it demonstrates concurrency/correctness semantics only. Snapshot accounting is conservative estimated accounting, not allocator-level proof. Sustained writes may repeatedly supersede compaction, and automatic maintenance has no background retry. No performance benefit or production readiness is claimed. The prior operation-specific capacity refusal remains binding: do not rerun that operation or bypass its unchanged preflight.
