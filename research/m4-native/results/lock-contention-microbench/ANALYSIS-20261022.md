## Interpretation and next work

This one small, single-arm run shows near-zero M4 query-lock waiting for this 64-document workload and the requested reader/writer/GC distributions. It does **not** compare against the old exclusive-lock implementation, estimate stable p95, establish a performance win, or prove behavior under larger collections/write backlogs. Do not compare its latency directly with earlier 500×5 results; workloads and code versions differ. Writer commit latency includes native flush work; no claim that the M4 state mutex causes that tail is supported. The result argues against making another lock change based on this measurement alone. Keep the writer-preferred lock and durability/correctness prototype unpromoted; next useful work is source-level attribution of the writer-side M4 state-lock hold and a separately bounded, appropriately contained diagnostic only if it can isolate that cause without changing the hard gates. No production changes or pushes.
