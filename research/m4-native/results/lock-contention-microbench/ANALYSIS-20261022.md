The 3 GiB reserve is a policy-selected per-operation value carried into the owner-authorized pair contract in commit `9a3c268` (also used by the scalar-open exploratory contract), not a platform safety standard.

The separate historical `M4-RG-MEM` threshold, 5,477,762 KiB from ten successful B3.1 arm-before receipts, remains a raw empirical-envelope comparison. The selected contention-aware pair/microbench mode records its FAIL but does not enforce it. Qualification and legacy modes retain their declared gates. Hard checks in this diagnostic remain: operation-specific `MemAvailable >= host reserve + cgroup memory cap` at admission; reserve preservation at runtime; approved disk reserve; finite/read-back cgroup caps; zero swap allocation; OOM/limit-event and host-distress checks; telemetry integrity; timeout; workload correctness; watchdog and verified cleanup. I/O PSI is retained as uncontrolled host context, not an admission/abort gate in this explicitly contention-aware mode.

Pair `m4-shared-collection-pair-20261022-040857-4ee12c` had 3,794,853,888 B available against its 4,294,967,296 B requirement and was refused before workload launch. Its receipt remains immutable; it was not retried.

## Interpretation and next work

This one small, single-arm run shows near-zero M4 query-lock waiting for this 64-document workload and the requested reader/writer/GC distributions. It does **not** compare against the old exclusive-lock implementation, estimate stable p95, establish a performance win, or prove behavior under larger collections/write backlogs. Do not compare its latency directly with earlier 500×5 results; workloads and code versions differ. Writer commit latency includes native flush work; no claim that the M4 state mutex causes that tail is supported. The result argues against making another lock change based on this measurement alone. Keep the writer-preferred lock and durability/correctness prototype unpromoted; next useful work is source-level attribution of the writer-side M4 state-lock hold and a separately bounded, appropriately contained diagnostic only if it can isolate that cause without changing the hard gates. No production changes or pushes.

The operation plan, exact command, host/cgroup/watchdog telemetry, workload samples, cleanup receipts and `SHA256SUMS.txt` are retained under `20261022/m4-lock-contention-microbench-20261022-042253-3aa79d/`. The initial 256 MiB abort is retained under its own operation root.

## Compaction tombstone snapshot memory

Source tracing found `MergeRuns` cloned the complete `tombstones_` unordered set, erased entries whose DocIds fall inside the compacted run range, encoded that filtered copy, and replaced the live set only after manifest publication. The candidate now encodes the filtered tombstone snapshot directly from the immutable live set, reserving the serialization vector for the exact retained count, and erases the compacted range in place only after the new manifest is durable. This removes a full hash-set clone during compaction while preserving the pre-manifest live set and the established publication order. The on-disk encoding still sorts IDs and uses the same count, delta varints, version, and checksum. `m4_correctness` (including compaction and fault/reopen cases) and the writer-preferred mutex test pass after this change. It has not been benchmarked because the last fresh operation was formally blocked by the unchanged capacity preflight; no memory/latency win is quantified.

Streaming-merge dictionaries also held transient owning copies of term names in both `FtsDictEntry` and `term_to_id`, plus owning value/field names in output dictionary records. The current prototype makes those fields `std::string_view`s borrowing from pinned input segments (field-directory names borrow from the local stable field-name set); the input shared pointers and set outlive dictionary serialization. The owned file bytes are still written before the merge returns. This avoids those transient string allocations without changing file format or the map API. `m4_correctness` plus the writer-preferred mutex test passed after rebuilding. `memory_limit_bytes` still charges the existing conservative dictionary estimate.

FTS merge also copied each iterator's positions into a nested `BuildPosting::positions` vector, then destroyed those per-posting buffers at every output-block flush. The candidate now stages posting metadata as offsets/counts into one contiguous `block_positions` vector, clearing it between blocks while retaining capacity for reuse. Reserved posting metadata, the reusable output-position capacity, and excess decoded input-iterator capacity are charged to the compaction memory tracker; retained capacity stays charged through the term. This avoids one owned vector/allocation per emitted posting and keeps scratch proportional to a block rather than a merged term. A new phrase regression creates two flushed runs, compacts them, then checks repeated phrase positions in the merged output; the correctness and mutex tests pass. A tight-budget regression verifies that large posting buffers trigger a pre-publication abort while old runs remain searchable. Query-side phrase checking now precomputes term-to-cursor indices once per query, borrows cursor position vectors, and reuses monotone scan indices instead of copying positions into per-candidate vectors/hash sets; the phrase fixture covers delta postings, v1 segments, v2 compacted output, and multiple simultaneous phrases. Neither dictionary views, contiguous merge scratch, nor phrase evaluation has a measured RSS/latency result: the operation preflight is still blocked and no performance win is claimed.
