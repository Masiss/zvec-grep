# M4 P3 root-cause triage — 2026-10-30

Scope: three unresolved items from the camera/Stage E investigation. This is evidence triage, not a new benchmark.

## 1. Watchdog cadence abort (219-file attempt)

**Finding: the watchdog itself was scheduled late; the workload did not violate a resource limit.**

Evidence from `M4-P3-STAGE-E2-ATTEMPTS-20261030/attempt2/pair-first/containment/runtime.jsonl`:

- 13 watchdog samples.
- The last inter-sample gap was **2.075409 s**, above the configured **2.0 s** maximum.
- Every other gap was ≤1.819 s.
- Sample read durations were **2.9–62.8 ms**, far below 2 s.
- `CLOCK_MONOTONIC` and `CLOCK_BOOTTIME` deltas agree; no suspend/clock-step signature.
- Host load at the last samples: **12.85 → 13.83** (1-minute average).
- The abort detail was `contention monitor cadence incomplete/nonmonotonic`.

Conclusion: the watchdog process woke **~1.5 s late** relative to its 500 ms sleep loop under host CPU contention. This is a **watchdog scheduling/telemetry cadence** failure, not an M4 correctness or capacity failure. It did not reproduce in the 300/421 camera runs.

No fix was applied. A safe fix would need absolute deadlines/timerfd or real-time priority, or an explicitly approved larger monitoring gap; changing the threshold would weaken the gate and needs owner approval.

## 2. Native 6 drops at 421 camera

**Finding: native queue saturation at 40 QPS; not an M4 defect.**

From `M4-P3-STAGE-E3E-CAMERA-421-20261030/pair-result.json`:

| Pass | Native accepted | Dropped | Queue p95 | Service p95 |
|---|---:|---:|---:|---:|
| initial_rescan | 256 | 0 | 119.3 ms | 134.5 ms |
| single_file_update | 100 | 3 | 139.0 ms | 5.1 ms |
| rename | 106 | 3 | 167.1 ms | 13.0 ms |
| delete | 16 | 0 | 99.1 ms | 47.5 ms |

Native dropped **3 + 3 = 6** offers during update and rename. Queue delay was 139–167 ms; the queue capacity is 8. M4 in the same run accepted **506/506** with zero drops.

Native service p95 was also higher than M4 in the early passes: initial rescan 134.5 ms vs 15.8 ms; update 5.1 ms vs 2.5 ms; rename 13.0 ms vs 6.2 ms. The immediate cause is **native service/queue saturation at 40 QPS**. The deeper reason native's initial-rescan service time is ~8.5× M4 was not decomposed further in this triage.

## Deeper native attribution (item 2)

The native 421 run shows the tail is not primarily native FTS work:

| Pass | Native store-lock p95 | Native FTS p95 | Native service p95 | Native queue p95 |
|---|---:|---:|---:|---:|
| initial_rescan | **133.03 ms** | 0.80 ms | 134.5 ms | 119.3 ms |
| single_file_update | 0.00 ms | 1.40 ms | 5.1 ms | 139.0 ms |
| rename | 0.00 ms | 1.30 ms | 13.0 ms | 167.1 ms |
| delete | 14.72 ms | 0.80 ms | 47.5 ms | 99.1 ms |

For initial rescan, native service p95 134.5 ms is almost exactly the native **store state-lock wait** p95 133.03 ms; native FTS p95 is only 0.80 ms. M4 in the same pass has store-lock p95 0.00 ms (p99 0.10 ms) and service p95 15.8 ms.

For update/rename, native store-lock p95 is 0, but the FTS tail is large: p99 43.23 ms / 66.64 ms, and service p99 106.8 / 111.5 ms. With queue capacity 8, a few long-tail queries fill the queue and cause the 3 + 3 drops. M4 avoids the native store-lock path (sidecar) and has service p95 2.5 / 6.2 ms with zero drops.

Deeper conclusion: native queries serialize on the **native index-store state mutex** during initial indexing and inherit a native FTS tail during mutation; M4's sidecar query path avoids that mutex. This is a native-path capacity limitation, not an M4 defect. The native FTS tail itself is not decomposed further.

## Handling the missing 421-file provenance (item 3)

The original corpus cannot be reconstructed from count/bytes/hash alone. Recommended handling:

1. Mark the original Stage E as **`PROVENANCE_BLOCKED`**, not a runnable corpus.
2. Treat the completed camera 421 run as a **new, explicitly named larger-corpus diagnostic** with its own manifest (`9bff98…`, 4,693,920 bytes); never label it Stage E.
3. Add a policy/test guard for future full-corpus references: require `source_repo`, `source_commit`, `source_selection`, and a verifier that recomputes the manifest; reject any reference with only count/bytes/hash.
4. If the original 421-file Stage E is contractually required, the owner must provide the exact snapshot or commit/selection that produces `a4d536…`. There is no safe technical workaround.

This closes the provenance question: the failure is missing source identity, not a build or M4 bug.


## Native FTS tail decomposition — feasible, and mostly already answered

The native library already has stage spans in `native_timeline`:

- `collection_query`: total, `schema_handle_lock`, `query_validate`, `get_all_segments`, `sql_engine_execute`
- `fts_recall_stage`: `schema_fetch`, `prepare`, `filter_compute`, `fts_search`, `result_fetch`

They are emitted when `M4_NATIVE_FLUSH_TIMELINE=1`. The 421 pair did not enable them, so the 43/66 ms FTS-tail values were not decomposed in that run.

Existing native-only trace R3 already shows the important result: native FTS p50/p95 0.549/1.383 ms, inner FTS recall stages <1 ms, and slow query waits dominated by `schema_handle_mtx_` / optimize-seal or flush holds. Therefore the 421 native FTS tail is most likely native schema-lock wait inside `CollectionImpl::query`, not FTS search. Exact 421 attribution needs one native-only run with `M4_NATIVE_FLUSH_TIMELINE=1`; the prior native-only authorization is consumed, so this needs fresh owner authorization.
