# M4 autonomous campaign checkpoint — 2026-10-26

## Latest milestone — cross-store publication fence and Gate A research proof (2026-10-26)

**Gate A: PASS for the opt-in research integration path; production integration remains REWORK.** The chosen architecture is a bounded durable pass-intent manifest plus a workspace writer/query fence, using fail-closed invalidation—not retained revisions—on interrupted multi-file publication. The manifest is fsynced before native `finalize_writes` publishes the staged mutation set; staged work may already exist, but the workspace fence and per-file status keep it from forming a mixed searchable snapshot. Only after native finalize succeeds are M4 per-file states published. Queries serialize behind the pass and therefore cannot combine native and M4 generations. If recovery finds an incomplete pass, every touched file is hidden/invalidated in both stores and daemon freshness stays dirty until a full source retry succeeds.

This deliberately follows the existing `zg-engine` per-file failure contract: beginning a replacement retires the prior searchable projection; a failed file is `NotIndexed`/failed and retried, not served stale. That trade-off is direct in `rust/crates/zg-engine/src/workspace/README.md` and `storage/store/mod.rs`. Stable untouched files remain searchable. This is not rollback to a prior revision. The research adapter retains no archived document revisions; it replaces/deletes file ordinals. Existing tombstone/WAL reclamation remains M4's flush/compaction responsibility and is not a lifecycle qualification claim.

**Why this architecture:** immutable revisions plus an active-set manifest would preserve rollback and concurrent old readers, but requires versioned native projections, retained-byte GC, and migration; no evidence currently justifies that cost. Per-file publication without a cross-store fence is cheaper but permits readers to observe mixed generations. The selected intent+fence option adds O(touched-files) manifest encoding/checksum and syncs (bounded to 2 MiB / 65,536 file IDs), no full-index copy or retained revision, and blocks queries for the duration of the writer pass. Query-wait/tail latency is not measured; large-pass latency remains a qualification risk.

## Work executed in this checkpoint

### Coordinator WAL publication invariant

Source review of `research/m4-native/tests/m4_bridge_integration.cc` found that recovery validated each coordinator WAL record's checksum and syntax, but previously did not enforce that a `P` (publish) record was preceded by a matching latest `R` (reservation). A syntactically valid `P 5` without `R 5` could advance the manifest. The normal writer's ordered, synced `R` → durable writes to both stores → synced `P` path does not produce that sequence through an ordinary crash, so this was a research-coordinator invariant gap rather than evidence of a current production P0.

Recovery now:

- treats records at or below the already-published manifest as historical;
- requires new reservations to increase monotonically;
- requires each new publication to match the latest reservation and advance publication order; and
- throws before rewriting the manifest on an invalid state.

Deterministic regressions cover an unreserved publish and a publish of an older reservation after a newer reservation; both assert failure, preserved WAL bytes, and unchanged manifest. The existing valid-final-record-at-EOF and torn-suffix tests remain covered.

**Coordinator journal resource audit:** `Coordinator::Commit` durably appends one `R` reservation and one `P` publication per successful generation. The canonical record length is at most 22 bytes (`uint32` decimal plus kind/checksum/newline), so each successful generation adds at most 44 bytes; interrupted attempts add at least one reservation. There is no total WAL cap or checkpoint, so file growth and recovery time have no absolute upper bound. `NextGeneration` calls `RepairWal` and then scans the whole journal; repeated commits therefore perform O(n) journal reads each and O(n²) cumulative scanning. `RepairWal` originally used unbounded `std::getline`; it now reads at most 64 bytes per line, fails closed and preserves an oversized complete record, and truncates an oversized unterminated suffix under the existing torn-tail rule. Added deterministic regressions for both outcomes; the full bridge correctness executable passes 4,684 checks. This bounds per-record allocation only, not total WAL size or replay time. A safe checkpoint cannot simply discard reservations: interrupted generation IDs must remain discoverable until `shared-gc.state` durably records `orphan_reserved_through` and GC has reclaimed the associated rows. No total-WAL checkpoint was implemented; coordinator lifecycle remains unqualified and must not be conflated with the M4 index WAL envelope.

## Architecture options and trade-offs (current decision)

| Option | Correctness / availability | Complexity and storage | Decision |
|---|---|---|---|
| Immutable per-file revisions plus atomic active-set manifest | Preserves prior snapshots and permits readers to keep using an old generation; clean rollback | Requires versioned native projections as well as M4, active-set GC, retained-byte budget and migration; no full-lifecycle evidence | Not selected: materially more machinery/storage than current contract requires |
| Durable pass-intent manifest + writer/query fence + fail-closed cleanup | No mixed native/M4 query snapshot; crash recovery hides every touched file and daemon retries. Affected files are unavailable until retry; unchanged files remain available | O(touched-file IDs) bounded manifest and sync cost; no full-index copy or archived revisions. Queries wait for the whole pass. Existing M4 WAL/tombstone compaction remains responsible for physical reclamation | **Selected for research Gate A** |
| Independent per-file publication without workspace fence | Lowest coordination cost and best per-file availability | Can expose mixed native/M4 state during a multi-file pass; unsafe for cross-store hydration | Rejected against the stated cross-store consistency contract |

This choice is scoped to the current engine contract, which already fails closed instead of retaining the previous file revision. It does not establish that the same availability trade-off is acceptable for every future product contract. No production wiring or performance advantage is claimed.

## Rust-to-M4 per-file FFI proof (continuation)

Implemented a research-only C ABI (`include/m4/rust_file_adapter.h`, `src/rust_file_adapter.cc`) and Rust crate (`rust-bridge/`). Per-file state is checksummed and atomically replaced; a single-owner file lock prevents two adapters from opening the same root. M4 rows remain hidden while a file revision is staging. Appends are fsync-WAL M4 mutations; publish requires all expected rows acknowledged, deletes any old ordinal tail, and then marks the revision indexed. An uncertain manifest write poisons the live handle so callers must close/reopen instead of observing stale in-memory visibility. The wrapper batches file staging and only publishes after a caller-supplied native commit succeeds; native commit failure rolls back to hidden/not-indexed state.

The standalone FFI tests exercise a 300-fragment replacement across bounded batches, reads between batches, top-K refill around hidden high-scoring old rows, shrink from 300 to 1, native-commit failure/rollback, malformed and oversized state, search-allocation bounds, single-owner enforcement, and a child-process exit after durable M4 staging plus a fsynced revision marker. Reopen keeps it invisible and permits retry. In addition, a test-only `zg-engine` test uses the actual `IndexStore`: it commits a staged native replacement and fsyncs it, exits before M4 publish, reopens the native and M4 stores, verifies M4 remains hidden while the native revision is durable, retries from source, publishes, maps M4 ordinals through the native manifest to canonical fragment IDs, hydrates through `load_search_hits`, and verifies the result after both stores reopen.

Cost/risk: this sidecar adds a second durable state path and extra per-file manifest syncs, plus M4 WAL syncs for each bounded batch; one handle serializes reads and writes. `stage_file` receives an already-materialized document slice, so it does not prove streaming peak-memory behavior. Query results expose file ID/revision/ordinal only; production must map ordinals through the published `FileManifest`, hydrate through the existing store, apply `StorageSearchFilter`, and refill after filtering. A crash after native commit but before M4 publish is fail-closed and retried from source, not rolled back to the old file revision. This remains research-only and does not establish watcher acknowledgement, ranking parity, migration, durability across power loss, or performance benefit.
