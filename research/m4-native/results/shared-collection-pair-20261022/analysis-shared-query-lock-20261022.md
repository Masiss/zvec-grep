## What instrumentation established

Baseline shared arm (20 concurrent reader samples): reader total p50/p95 5.896/9.829 ms; generation pin p95 0.008 ms; coordinator snapshot-lock wait p95 0.001 ms; M4 query-lock wait p50/p95 4.255/7.888 ms; FTS-stage p50/p95 4.363/8.382 ms; vector 1.505/3.358 ms; merge 0.020/0.032 ms. The old M4 `recursive_mutex` serialized queries as well as writers. Thus the principal observed wait is inside M4, not generation pin or coordinator snapshot lock.

Prototype shared arm: reader total p50/p95 6.564/7.439 ms; pin p95 0.010 ms; snapshot wait 0; M4 shared/exclusive query-lock wait p50/p95 4.220/5.029 ms; FTS stage 4.407/5.415 ms; vector 1.573/2.426 ms; merge 0.022/0.038 ms. Writer commit p50/p95 62.611/69.687 ms, GC 20.465/23.969 ms, cycle 77.938/88.249 ms. This single arm cannot establish a change: median was not better, p95 shifted favorably, and host/operation variability plus arm incompleteness prevent causal comparison. Note that the wait metric's lock changed semantics: baseline exclusive recursive mutex (reader + writer queue); prototype reader/writer lock (writer contention only for concurrent readers).

Source interpretation: `SearchFtsFiltered` held the global recursive mutex for the whole FTS query. The prototype lets uncached filtered readers share a `shared_mutex`; mutation APIs take it exclusively, preserving old-or-new state visibility. Cache-enabled filtered queries remain exclusive. Unfiltered `Index::SearchFts` still uses the state mutex and is outside the prototype's shared-reader path; the shared-collection coordinator workload uses filtered search (`FilterExpr::All()`), so keep this change scoped to that measured route. In the prototype, readers still wait on writer-owned critical sections (`ApplyBatch`/`Flush`); their exclusive duration is the next optimization target. This is evidence for shared-reader admission, not a final architecture selection.

The committed follow-on code preserves state-mutex serialization but postpones `ApplyBatch`'s exclusive query lock until the durable WAL frame exists, then releases query exclusion during `FlushInternal`'s local segment build/write and reacquires before in-memory state or manifest/tombstone/WAL publication. It preserves WAL-before-apply and manifest-before-WAL-reset. Source audit confirms all visible mutators/compaction and reclamation paths hold the exclusive query lock; readers either hold the shared query lock (`SearchFtsFiltered`) or the state mutex. During the unlocked segment build, the state mutex prevents writers and the implementation only reads the unchanged in-memory query-visible state. A bounded test-only barrier now pauses after segment write/open but before in-memory/manifest publication; the integration reader completes with the exact expected full delta snapshot, then the writer resumes. The bridge suite passed 4,636 checks/0 failures; focused M4 correctness rebuild/CTest also passed. Cache-disabled and cache-enabled full bridge correctness/durability/crash suites on the preceding code each passed 4,633/0, with cache-enabled exercising the exclusive query-lock branch. Operation `013803` predates this follow-on and is not performance evidence for it.

Deterministic post-append barriers prove readers complete before apply and then observe updated/deleted state. A dedicated short mutex protects filter-cache state, and all read-only FTS/hybrid/scalar search entry points now use shared query admission: cached/uncached `SearchFtsFiltered`, `SearchFts`, `SearchFilter`, `SearchHybrid`, `SearchInvert*`, and `SearchArrayUint32`.
