## Authority and interpretation

The active user instruction authorizes the operation. Repository-wide mission and execution rules are in root `AGENTS.md`; M4 design/workflow constraints are in `research/m4-native/AGENTS.md`. `benchmark-policy.json` is the sole machine-readable source of resource-guard values and classifications. This Markdown document explains policy meaning and control flow; it is not parsed by enforcement code and intentionally does not duplicate numeric thresholds. Guard values are owner-controlled.

The historical resource thresholds derive from the successful B3.1 arm-before envelope preserved in the canonical M4 handoff and result artifacts. They are empirical descriptors, not a validated model of universal host safety. Only explicitly enforced capacity/containment checks (such as retained disk and applicable SwapFree) can refuse or terminate an operation; raw host PSI/load/MemAvailable comparisons cannot. I/O PSI is host-wide, not an arm-specific I/O cap.

Do not change a threshold, weaken an assertion, or bypass a refusal in research code without explicit owner approval. An amendment must include the proposed values/classification, evidence and uncertainty, risk assessment, fallback/rollback, acceptance tests, and an update to this JSON, this document, `RESULTS.md`, and the canonical handoff. A resource refusal alone is not evidence that a threshold should be changed.

### Monitoring and abort contract

Before/during/after each arm retain host PSI (CPU/memory/I/O), MemAvailable, swap and reclaim/OOM counters, shared filesystem/diskstats, owned cgroup CPU/memory/swap/PSI/task counts and task-limit events, process-tree PSS/RSS/swap/I/O, workspace measurements and lifecycle receipts. Native stages remain in the existing stdout timeline; no heavy tracing is enabled. Compare ambient/during host pressure and owned CPU/memory separately. `contention-analysis.json` reports temporal pressure differences and explicitly cannot identify a causal incremental M4 effect from a concurrent uncontrolled host. The process-tree collector retries up to three times when cgroup membership changes during `/proc` reads; persistent churn or an unreadable live member remains incomplete required telemetry and fails closed. Process-tree I/O snapshots can lose exited workers and are not device write attribution.

Required safety/workload telemetry must be present, finite, in range, internally consistent and monotonic. Host PSI/load/MemAvailable are optional observations; missing or malformed values never invalidate an operation. This mode uses the plan's explicitly bounded maximum observation gap and actual read brackets rather than requiring nominal idle-host sample cadence. Missing/overlong required coverage blocks; reduced but valid resolution is disclosed. For contention-aware M4 operations, the independent watchdog records both `CLOCK_MONOTONIC` and suspend-inclusive `CLOCK_BOOTTIME` and enforces the configured maximum against both inter-sample cadence and current-sample duration; unavailable boottime support fails closed. #### Four-arm writer/compaction contention diagnostic

`tools/run_lock_contention_microbench.py` binds each unique operation to the content-hashed `m4_compaction_writer_contention` binary and Jieba dictionary. Each arm seeds 8,192 documents, runs one compaction with four concurrent writers and two readers (32 queries each), then Flushes and verifies after reopen. The `default`, `snapshot`, and `snapshot_rebase` arms use four WAL-durable writers making eight individual Upsert calls each. The `apply_batch` arm submits the same 32 logical mutations as four atomic, WAL-durable `ApplyBatch` calls (eight mutations per writer) while using default compaction. It compares explicit client batching, not an internal autonomous group-commit queue. Writer timings are per API call: 32 Upsert samples versus four ApplyBatch samples. Their p95s have different units and sample counts and are not equivalent tail measures. The three compaction strategies include default, the snapshot prototype (which aborts publication on concurrent state change), and a research-only snapshot-rebase prototype. With WAL enabled, rebase mode preserves concurrent writes without synchronously flushing pending deltas at publication: it scans uncommitted WAL deletes, updates affected run dead-count/tombstone accounting, publishes only through the prior durable WAL sequence, and leaves the delta WAL-backed for later normal flush/replay. The WAL-disabled fallback retains its pending-flush path. It replaces only immutable runs captured at build start and does not change the default API path. Arm order is randomized by reversing the fixed set from the unique operation root hash. The harness records per-call writer/reader latency plus opt-in write-stage wall/CPU telemetry for normalization, state-mutex wait and hold, WAL encoding/append, query-mutex wait, apply, and auto-flush. The state-lock hold timer pauses while snapshot merge builds unlocked. ### Remaining limits and launch decision

Cgroup memory/CPU caps constrain only the owned service, not the external observer. Host reserves must account for observer/kernel needs and other active work; approval is an operational risk decision, not a universal safety guarantee. I/O interference, shared Btrfs allocation races, page-cache effects and sampling gaps remain possible. A sampled workspace guard can overshoot between reads; no kernel disk quota or per-arm I/O hard cap exists. Kernel OOM/cgroup events and reserves cannot predict every global failure. The observer itself can add scheduling and I/O pressure.
