## Question and scope

Measure whether Potion Code 16M v2 distinguishes source evidence for a described behavior from hard negatives, then test whether source representation changes that signal. Keep this separate from ANN acquisition, fusion, entity cutoff, evidence packing, answer generation, and product gain.

Use the pinned public C# source lock only. No private HRM or RAG validation, no a02, a03, val-03, or other previously exposed query as an independent example. Exclude known target files BufferedTokenStream.cs, TokenStreamRewriter.cs, UnbufferedTokenStream.cs, JsonTextReader.cs, JsonWriter.cs, and known Dapper task targets SqlMapper.cs, DynamicParameters.cs, SqlBuilder.cs. Source-version comparison is measurement evidence, not an annotated benchmark group.

## Groups and split

Target **40 behavior groups**: five mutually exclusive primary groups in each of eight categories below. Each group has one question and two meaning-preserving paraphrases; paraphrases stay with the group. Use one primary target source file per group; cross-file evidence may add linked files, which are reserved to the same split. Assign related behavior, copied-code, overload-family, inherited-contract, or duplicate-source groups together under a behavior_family_id; a family may not cross the split.

- Development: 24 groups from ANTLR C# files (three groups per primary category).
- Held-out evaluation: 16 groups, eight from Dapper and eight from Newtonsoft.Json (one group per category per repository). Neither repository supplies development labels or representation choices.
- Split by repository and file before writing queries. No source file, entity, behavior family, or paraphrase crosses splits.
- With five total groups per category and only two held-out groups per category, category results are **descriptive only**. This study cannot establish category-specific reliability; do not promote one from a sparse cell. Report held-out aggregate results and both held-out repositories separately.

The eight primary categories are: (1) implementation vs documentation about the same symbol; (2) declaration/interface vs definition; (3) neighboring methods with shared vocabulary but different behavior; (4) similar names with different conditions/state; (5) behavior query without implementation identifiers; (6) complete method vs a fragment missing a necessary operation/condition; (7) multiple source ranges and jointly required ranges; (8) documentation/declaration is the correct evidence type. The current category-7 draft has only jointly required sets. Alternative-sufficient-set discrimination is unavailable in this version; do not report an alternative-set metric unless a score-blind reviewed group is added before freeze. Category 8 prevents an “implementation always wins” bias.

## Annotation and candidate identity

Each group records repository/revision, locked path and file hash, split, family ID, primary/additional categories, source-derived query provenance, and whether every query avoids exact target identifiers. A source-based independent reviewer checks relevance before scores are available; adjudicate disagreements then, and freeze exclusions before scoring.

Represent relevance as **evidence sets**, not one binary label per overlapping fragment:

- An alternative set is any one independently sufficient range-set.
- A required set contains all source ranges jointly needed for the requested claim.
- A candidate may be sufficient, partial (supports a named subclaim), non_supporting, ambiguous, or not_applicable for a representation. Partial candidates are not counted as complete positives or hard negatives; category 6 also receives a separate preregistered complete-versus-partial rank diagnostic.
- Every evidence range is an exact half-open byte interval plus expected substring hash. For source bytes physically present in a fragment, a candidate can support the range only when its source interval contains it; overlap alone is partial. If a long required range crosses fragments, split it into ordered, gap-checked required subranges with explicit subclaim IDs. One candidate may satisfy several range IDs.
- **R0 metadata provenance is an explicit second source path.** Code metadata can carry documentation bytes outside a candidate's physical fragment interval. Such a candidate may be considered for that documentation only when a provenance record maps the exact metadata field/text to a locked source byte range and the full serialized R0 input is inspected. It is never inferred from symbol ownership alone. Record `physical_source` and `metadata_source` separately in candidate eligibility. Adjudicate the complete visible R0 input.
- Each frozen evidence range records its exact source interval and hash, R0-visible candidate IDs, and whether each ID provides the bytes physically or through verified metadata. Candidate whole-query labels are separate. For the 11 pairwise groups, store explicit supporting and non_supporting candidate-input IDs with a rationale; partial and pending inputs are excluded from that denominator. Pending candidates in rank-only groups remain unjudged and are never coerced to non_supporting. A class/ancestor fragment containing positive behavior cannot be labeled negative merely because it also overlaps a sibling negative range. Candidate roles are query-specific: one candidate may support several positive requirements, but cannot be both supporting and non_supporting for the same query. If role lists overlap, adjudicate them or exclude that candidate from the pairwise denominator; never score it as both sides.
- A hard-negative rationale must say why that range cannot support the requested evidence type/claim, not merely why another range is better. Documentation can be positive for contract questions.
- Unresolved/ambiguous groups are excluded from the primary denominator by a fixed rule before scoring.

Candidate identity is (source_revision, path, entity_id, fragment_id, half_open_source_byte_range). Preserve overlapping class/member entities and their distinct metadata; do not collapse them before vectorization. Also derive a physical_range_equivalence_id for exact duplicate source intervals. Report raw candidate rank and first rank after collapsing identical physical ranges. This avoids counting one byte range twice as independent relevance evidence while still measuring duplicate-vector crowding.

Use split-specific curated corpora: development pools contain the selected ANTLR files only; held-out pools contain the selected Dapper and Newtonsoft.Json files only. No file is present in both split corpora. The exact 51-file scratch source inventory, hashes and pool counts are frozen in the manifest. Define local=all R4 fragments in every file needed by its evidence sets, file=the primary file's fragments, curated-repository-slice=all candidates from selected files in that repository, and curated-split-corpus=all selected files in that split. These are sampled competition pools, not complete repository searches. Excluded previously exposed target files are absent from every pool.

For nested pool sizes 25/100/500, always include all annotated candidate IDs, then append remaining candidates ordered by the lexicographic hex digest of SHA-256 over UTF-8 bytes of the seed string zg-indexed-semantic-v1-pool, a NUL byte, group_id, a NUL byte, and candidate_id. If annotated IDs exceed k, actual size is the annotated count; record overflow. This pool recipe and ordering is identical across representations. Record pool sizes, entity/fragment provenance, physical-range duplicates and source-byte coverage. Do not use top-k acquisition to define the primary pairwise set.

## Frozen document/query representations

Use exact R4 v3 source e7d0a89c27e199489ea4ad786c619211bad5ac2d, C# Tree-sitter 0.23.5, exact source lock, cached Potion weights/tokenizer, cosine-normalized 256D vectors, and the R4 v3 model input builder. Do not use or rebuild a protected index.

For R0–R4, preserve the same candidate identities and source-byte anchors. Query embeddings are identical across document variants. Candidate-owner lists are complete, sorted by (absolute start byte, end byte, symbol name), and may contain multiple owners. Never select a best owner from relevance labels.

- **R0 current:** exact R4 v3 vector_content_for_fragment, including code metadata order and 473 UTF-16-unit metadata cap for the 1,894-unit budget; C# scope omission remains as implemented. Record all emitted content parts.
- **R1 body intersection:** retain only candidate bytes that intersect executable method bodies; no metadata. Non-method, documentation-only, and declaration-only candidates are not_applicable, not silently dropped.
- **R2 signature + body:** for every overlapping method, create one owner record with exact signature and that candidate’s body intersection, in the frozen owner order. No documentation text.
- **R3 qualified owner + body:** create one owner record per method with fully qualified scope, symbol name, signature and body intersection; no documentation.
- **R4 fragment + structure:** preserve full R0 fragment and R0 metadata, then append one deterministic compact JSON record per overlapping function node. Fields, in fixed order: kind, name, scope, has_body, declaration_overlap, fragment_contains_full_method, method_contains_full_fragment, body_overlap_ratio, documentation_overlap. body_overlap_ratio is intersection bytes divided by AST body bytes, rounded to six decimals; documentation_overlap is boolean. Sort owners by (absolute start byte, end byte, symbol name). Use JSON string escaping; absent fields are null and zero-owner lists are []. R4 may keep documentation already present in R0 entity metadata, but adds no owner documentation/signature or raw source text outside the fragment.
- **R5 method unit (separate architecture track):** one unit is the full method declaration and body, not separate declaration/body units; interface/abstract methods without bodies are declaration-only units. Exclude properties/accessors and keep local functions inside their parent method. Long methods split with a 1,421 UTF-16-unit source window (1,894 nominal units minus the 473-unit R0 metadata reserve) and 284 overlap; each chunk keeps identical R0 method metadata and absolute offsets. Use the same 1,024-token model cap. Because candidate units/evidence coverage differ, do not compare raw Recall@k or pairwise denominator to R0–R4. Report own unit count, coverage and byte-budget-normalized results.

Serialization is frozen as UTF-8, LF-delimited compact JSON with explicit field order and JSON escaping. R1 has only ordered body-intersection strings. R2/R3 use a JSON object with an owners array; owner records are ordered as above and fields are scope, name, signature, body, with absent fields null. R4 appends a newline, the structure-v1 marker, another newline, then a JSON owners array with the fixed fields listed above. Empty owner lists serialize as []. Ratios use f64 rounded to six decimals. For R1–R3, replace each parsed comment span by one ASCII space and preserve its original CR/LF bytes; store a segment map from every retained transformed byte interval to its original source interval, while inserted whitespace maps to null. This preserves token boundaries and offset provenance without passing removed comment text.

R0 preserves comments as source text. R1–R3 use only syntax body spans after the comment transformation above. R4 adds only structural metadata tags, not owner documentation or source text outside the R0 input.

The primary fixed-source comparison does not force equal token counts: metadata is part of the treatment, and may displace source at the 1,024-token cap. Save exact input text/hash, token IDs and offsets, retained source intervals, truncation flag, and whether each annotated required range/operation survives. A truncated decisive range is not evidence of semantic discrimination failure.

For the secondary equal-budget ablation, use a separate source-first serializer for R0m–R4m: source/body bytes first, followed by metadata in fixed priority scope/name, signature, structural tags; R0m includes current entity metadata. Tokenize each full string, then keep at most the first N IDs where N is the exact token count of that candidate's untruncated R0 input, capped at 1,024; shorter inputs stay shorter. Query text and source anchors remain fixed. Compare R1m–R4m only to R0m, never to current R0. Save retained token offsets/fields.

Do not add gold summaries, target method names to queries, or generated behavior text to documents. Keep current source comments in R0 as they occur; R1–R3 use syntax body spans with parsed comments removed; R4 keeps only the documentation text already in R0 metadata.

## Controls and metrics

On the identical candidate identities, compute:

- Direct cosine for R0–R4 with query vectors fixed.
- BM25 over the exact R0 text retained after the same 1,024-token truncation, using a frozen tokenizer that splits C# camelCase/snake_case and normalizes case; freeze BM25 k1=1.2, b=0.75, corpus IDF and tie policy. Also report a secondary BM25 over full pre-truncation R0 text.
- Exact symbol/scope alignment, with usable-query coverage reported; identifier-free queries make this a limited control, not a deliberately weakened baseline.
- Equal-weight reciprocal-rank fusion of vector and BM25 (k=60) as a fixed complementary control; no tuned weights and no FTS/vector raw-score mixing.

For the narrowed R0 round, score the frozen 40-group required-range rank set and the separate 11-group/15-pair input-instance diagnostic. Do not treat the rank-only groups as exhaustively relevance-labeled. Before any R1–R5 comparison, derive one fixed common eligibility mask: include a group/pair only when every required range and hard-negative input is applicable to all compared representations and its decisive bytes survive each transform. R1–R3 body-only transforms may exclude documentation/declaration evidence categories; report retained groups and category counts, then recompute R0 on that same mask. A smaller denominator is never a gain.

For the frozen R0 range-rank diagnostic, a range is available only through the frozen `candidate_ids` membership in its evidence-range record: full visible physical bytes or a verified metadata range. Candidate whole-query labels do not replace these range memberships. Exact duplicate candidate intervals are one physical range for range completion, but each embedding remains in the raw rank report. For pairwise comparisons, use only the explicit 15 candidate-input pairs in the frozen roster. For a required positive evidence set, compute each unique required range's score, then use the **minimum** (weakest necessary piece). For alternatives, use the maximum of their set scores. Hard-negative input instances are evaluated individually or by the maximum score over adjudicated non-supporting candidates; never use a weakest shard to suppress a strong distractor. A candidate satisfying several required ranges can supply each one; completion rank is when retrieved candidate IDs cover all required range IDs. Partial candidates stay out of hard-negative pairwise win rates and are reported in a separate complete-versus-partial diagnostic (complete evidence rank, partial candidate rank, and group-level ordering). Supporting ancestors are excluded from negative candidate IDs even if they contain negative sibling bytes. If no eligible candidate supplies an evidence range, mark it unavailable in that representation and report it as a retrieval/representation coverage failure, not an embedding loss. For cosine, use tie tolerance 1e-6 and ties worth 0.5; for BM25/RRF, exact ties are 0.5. Average eligible positive-vs-negative comparisons within paraphrases, then within group; pairs and paraphrases are not independent samples.

For each required set, completion rank is the maximum first rank of its unique required ranges; for alternatives, use the minimum completion rank across sets. Because rank-only candidates are not exhaustively judged for relevance, report annotated required-range completion@1/5/10/20, complete-set coverage and completion rank, not exhaustive-relevance Recall or MRR. Report local/file/curated-repository-slice/curated-split-corpus and rank/coverage at frozen pool sizes 25, 100, 500, repository-slice and split-slice. Record underfilled pools (notably Dapper's 373 candidates). These retrieval-score pools do not measure index/ANN candidate acquisition. For category 6, report complete-versus-partial ordering separately from sufficient-set-vs-hard-negative pairwise scoring. For category 7, report complete jointly-required-set coverage. The alternative-set metric is unavailable in the current draft because none of its five groups has multiple alternative sufficient sets.

Uncertainty is descriptive and paired: 10,000 stratified bootstrap resamples of connected source-file/behavior-family clusters within the two held-out repositories, plus exact group win/loss counts and per-repository effects. Never resample paraphrases or source-overlapping groups as independent units. With only two held-out repositories and two held-out groups per category, do not claim population-wide or category-specific confidence. Report these limits.

Predeclared interpretation gates:

- A representation is a **candidate for further integration experiments** only if held-out macro group score improves by at least 5 percentage points over R0, improves on both held-out repositories, and has no high-confidence regression cluster. This is a screening threshold, not statistical proof or product promotion.
- Before scoring, assign one failure-mechanism tag from docs_over_impl, wrong_sibling_behavior, symbol_collision, declaration_vs_body, boundary_missing_operation, multi_range_incomplete, query_vocabulary_gap, or other. A high-confidence regression cluster is either (a) at least three held-out groups on distinct files, spanning both repositories, with the same tag and an R0-relative group-score regression of at least 10 percentage points, or (b) at least four such groups in one repository. Also report any individual wrong-order margin <= -0.10; one such failure is a counterexample, not a cluster.
- Call the vector signal **better than lexical in this sample** only if R0 exceeds BM25 by at least 5 points on held-out macro group score and beats it in both held-out repositories. Otherwise report mixed/no demonstrated advantage.
- Call vector + lexical **complementary** only if fixed RRF improves the same held-out macro score by at least 5 points over the stronger standalone baseline and adds at least two complete evidence sets at k=10 without increasing high-confidence regressions.
- A model limitation requires persistent hard-negative failure across R0 and structurally reasonable R1–R4, with decisive evidence retained. If results are mixed, call INSUFFICIENT_EVIDENCE.
- Select any candidate representation using only development groups. The single held-out pass tests the frozen candidate; do not select among held-out winners. Allow rerun only for recorded infrastructure/execution faults, never changed scores or annotations.

## Cost, integrity, and freeze gates

Record exact repository/source hashes; model/tokenizer hashes; rustc/build profile; CPU model, threads, batch size, repetitions and cache policy; parse, transformation, tokenization, query embedding, document embedding and ranking time; model load separate from warm inference; peak RSS; unique vs duplicate input count; candidate/vector/storage counts and bytes; total candidate tokens; and per-representation truncation. Mapping cost must distinguish full-file parse, entity-local parse, per-request reuse and no cross-request cache. Candidate-pool sizes are fixed before scoring.

Before Sol review: complete all 40 groups and candidate pools; verify every byte range against locked file hashes; manually verify a sample of declaration/body/doc offsets independently of the shared parser; check family/source split; exact identifier leakage; duplicate physical ranges; positive/negative rationale; required-set logic; lengths/comments/vocabulary and truncation. The score-blind validator may inspect annotations before freeze but must not see any model scores.

The embedding/ranking runner receives only queries, candidate IDs/provenance, and transformed document inputs; it must not read relevance labels, required-set IDs, rationales, or annotation files. Freeze and hash runner inputs, then write vectors, scores, ranks and truncation receipts; hash the complete output before a separate deterministic scorer joins labels. No score-dependent input or pool changes are allowed.

Submit actual task/range/label artifacts, source facts and this contract to fresh-context GPT-6.1 Sol High for score-blind annotation and design review. Resolve all findings before hashing/freezing. Run primary model scores once after freeze; no task edits or representation changes afterward. A final fresh Sol High review receives actual code, per-group results, failures and cost.

R0–R4 measure representation on fixed candidate anchors. R5 measures a changed retrieval unit. Direct embedding ranks do not establish ANN/acquisition, fusion, entity-cutoff, evidence-packing or answer-quality gains. Keep those as separate later experiments; do not run answer trials unless an integrated development prototype passes its existing evidence gate.
